# Исследование: что мы проверили и чем отличаемся

## 1. Задача

Владелец: «Есть счётчики Элехант, которые передают данные о потреблении воды в
широковещательном диапазоне — приложение не нравится, расшифруй передачу,
сопоставь со счётчиками, там есть температура воды и текущие показания».

Приборы: СВД-15 (холодная вода) и СВТ-15 (горячая, два тарифа). Приложение
«Счётчики Элехант» 5.1.1.

## 2. Метод

1. Полное прослушивание BLE-эфира без фильтров, сохранение **каждого** пакета.
2. Сопоставление manufacturer data с открытой картой
   [`vooon/elehant-to-mqtt`](https://github.com/vooon/elehant-to-mqtt/blob/master/docs/protocol.md).
3. Независимая сверка с orycan.ru (декомпиляция APK): раскладка полей совпала.
4. Сверка с экраном приложения по каждому прибору.
5. Аудит: какие байты постоянны, какие меняются; накопление истории.
6. Разбор платы: nRF24LE1, UART, SPI-программирование.

## 3. Что совпало с другими

- транспорт: только BLE-реклама, без GATT;
- `0xFFFF` — Элехант, `0x80` — признак;
- тип/модель, серийник, показания 0.1 л, температура 0.01 °C;
- заряд — байт 13 (у нас гипотеза, облако подтверждает наличие поля);
- B1 — служебные пакеты (в открытых источниках без расшифровки).

## 4. Чем мы отличаемся

### 4.1. Два канала 03/04 — это два регистра, а не «дубль»

Открытые таблицы: `03` и `04` оба названы «СВТ-15». Почему два кода — не
объяснено. Мы измерили: **03 — объём ниже +40 °C, 04 — выше +40 °C**. Это
подтверждается двумя разными показаниями одного прибора и логикой перерасчёта.

### 4.2. Температура холодной воды

Приложение её не показывает; прибор отдаёт то же поле (14–15), что и горячий.
Мы читаем и используем: это независимый датчик температуры трубы/стояка.

### 4.3. Сверка «до последнего знака»

Показания совпали с приложением: 246.8836 / 1.9967 / 0.5170 / 1.2417 м³.
Расхождение — только округление табло (0.1 л против 1 л).

### 4.4. Сохраняем каждый пакет и аудит

Не только «последнее значение»: каждая передача — строка с секундой. `--audit`
показывает, какие байты меняются. Это позволяет проверять заряд/флаги и ловить
«молчащие» приборы.

### 4.5. B1-пакеты

Сохраняем целиком, включая адреса вне реестра; hypothes: серийник/поверка.
В открытых источниках их не разбирали.

### 4.6. Чиповая часть

nRF24LE1-F16Q24, 8051, 16 КБ флеш, 2,4 ГГц; UART и SPI-программирование.
Разобрано, что можно снять по воздуху, а что только программатором.

### 4.7. Интеграции

Не «скрипт для чтения», а полный контур: Windows/Linux → MQTT → Home Assistant →
PostgreSQL/Grafana; ESP32-proxy для дальнего счётчика.

## 5. Практический результат

- приложение больше не нужно для чтения (но нужно для отправки в РСО);
- расход по часам/суткам, ночной проток, температура;
- два тарифа СВТ читаются раздельно;
- холодная вода даёт температуру, которой нет в приложении;
- данные можно сверять с облаком, не доверяя облаку.

## 6. Честные ограничения

- пакеты приходят редко без расхода (паузы до 15 минут);
- радиус: через стены/металл плохо; ESP32-proxy ближе к стояку;
- заряд — гипотеза;
- байт 16 не расшифрован;
- B1 не расшифрован;
- газовые приборы проверены меньше;
- прошивка/настройки по воздуху не читаются;
- облако — персональные данные, в публикацию не идут.
