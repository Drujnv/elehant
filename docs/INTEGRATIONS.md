# Интеграции с умным домом

## 1. Общая схема

```
Элехант (BLE-реклама)
   │  B0:* / B1:*  (0xFFFF)
   ▼
BLE-приёмник: Windows/Linux или ESP32/ESP32-C3
   │  MQTT
   ├──► Home Assistant (вода/газ, температура, батарея)
   ├──► PostgreSQL → Grafana (расход, ночной проток)
   └──► Telegram/уведомления (протечка, молчание прибора)
```

Прибор **не подключается** GATT-ом, поэтому приёмник только слушает эфир и не
занимает устройство.

## 2. Windows / Linux

`windows/elehant_reader.py`:
- слушает manufacturer data `0xFFFF`;
- декодирует объём/температуру/тип/номер/батарею;
- печатает JSON (можно направить в MQTT-мост).

Для MQTT можно использовать готовый Paho-мост (пример в `homeassistant/`) или
интегрировать в свой сборщик.

## 3. ESP32 / ESP32-C3 (BLE-proxy)

Зачем: счётчик может быть далеко от сервера; ESP32 ставится рядом со стояком,
ловит BLE-рекламу и публикует в MQTT по Wi-Fi.

Рекомендации:
- ESP32-C3 справляется, но чувствительность ниже ESP32-WROOM-32; для дальнего
  счётчика лучше ESP32 с внешней антенной;
- питание 5 В USB или 3,3 В;
- MQTT retained для последнего значения + отдельный топик `last_seen`;
- прошивка не требует сопряжения (только сканирование).

Готовый парсер: `esp32/elehant_decode.c/.h`; пример — `esp32/README.md`.

## 4. Home Assistant

`homeassistant/elehant_mqtt.yaml`:
- `sensor.elehant_<name>_water_m3`
- `sensor.elehant_<name>_temperature`
- `sensor.elehant_<name>_battery_raw`
- бинарный сенсор «нет данных N минут» (протечка/молчание)
- два канала СВТ как отдельные сенсоры.

MQTT-топики предлагаются:
```
elehant/<device_id>/volume_m3
elehant/<device_id>/temperature_c
elehant/<device_id>/battery_raw
elehant/<device_id>/packet_counter
elehant/<device_id>/rssi
elehant/<device_id>/last_seen
```

## 5. PostgreSQL / Grafana

Схема (пример):
```
home.readings(device, metric, value, unit, ts_iso, ts_epoch, source)
source = 'elehant'
metric = volume_m3 | temperature_c | battery_raw | packet_counter
```

Панели:
1. показания по приборам (последнее);
2. расход по часам/суткам;
3. ночной проток 01:00–05:00 (поиск течи);
4. температура холодной/горячей воды;
5. «молчание прибора» (нет пакетов > 30 мин).

## 6. R4S/ESP32-шлюз (Redmond)

R4S-форк заточен под Redmond, но его BLE-сканер можно использовать как
дополнительный приёмник, если он рядом со счётчиками. Это **не** готовая
интеграция: нужен отдельный обработчик/топик. Для публикации — только описать
идею, не обещать готовый код.

## 7. API для 1С и личный кабинет

Производитель заявляет **API для интеграции с 1С**. Это отдельный, официальный
канал обмена; условия/лимиты — у производителя. Второй способ — данные из
**личного кабинета**; конкретный метод не описываем, чтобы не тиражировать
неподтверждённый реверс — обращайтесь к производителю.

Наш BLE-контур работает **без** этих каналов; API/кабинет нужны для сверки,
официальных выгрузок и, при желании, интеграции с 1С.

## 8. Облако Элехант

`cntdev.ru` (WebSocket) даёт независимую сверку и знает заряд/температуру/
прошивку/дату поверки. Но:
- логин/пароль/API-ключ — **секреты**;
- персональные данные — **не публикуем**;
- `GET_HISTORY` у нашей роли заблокирован;
- в публичном проекте облако — только раздел «как сверить», без доступа.

## 8. Что важно для владельца

- приложение всё равно нужно для **отправки** показаний в РСО;
- наш контур — для **контроля и анализа**, не для замены учёта;
- данные прибора точнее приложения (0.1 л против 1 л);
- холодная вода даёт температуру, которой нет в приложении;
- при пропаже пакетов — сначала проверить радиус/питание, не «счётчик сломался».
